# Maestro Project Knowledge

## Project purpose

This website is a helper application I build as an extra contribution at work.

Its goal is to make colleagues' everyday work easier.

Prefer practical usefulness over technical complexity.

A feature should solve a real workflow problem rather than merely demonstrate an architectural idea.

## Users

The primary users are colleagues at a flour company.

They are generally not highly technical.

Design features so users do not need to understand:

- HTML
- APIs
- Database concepts
- Internal IDs
- Technical validation terminology
- Developer-oriented error messages

The interface should guide them toward the correct result.

## Developer context

I already understand the foundations of my project and its architecture.

Do not explain basic programming concepts unless I ask.

When explaining implementation decisions:

- Be direct
- Refer to the actual project structure
- Explain trade-offs when they matter
- Avoid unnecessary introductory material

## Architecture

The project uses a Maestro-based MVC approach.

Important architectural conventions include:

- MVC
- Repository Pattern
- Controllers
- Twig templates

Preserve these patterns.

Data access should normally remain in repositories.

Controllers should coordinate requests and responses rather than becoming large containers of unrelated business logic.

Twig is the main rendering layer.

For normal server-rendered behaviour, prefer:

`repository → controller → Twig`

Do not replace this with an API-driven architecture without a concrete reason.

## APIs

APIs are appropriate when they provide clear value, for example:

- Dynamic frontend interaction without a page reload
- Reusable data access across multiple UI areas
- More than one client needs the same endpoint
- Existing project conventions already use an endpoint for similar behaviour

Do not introduce an API merely because it is a modern pattern.

## Relevant business workflows

Examples of useful project functionality include:

### Nutritional calculations

Colleagues may need to:

- Enter ingredient values
- Enter recipe weights
- Enter percentages
- Calculate resulting nutritional values
- Copy the result into the webshop

The objective is to remove manual calculation and reduce mistakes.

When building calculation tools:

- Make units clear
- Validate ranges
- Explain unusual inputs
- Prefer direct usable output
- Consider rounding carefully
- Avoid requiring colleagues to understand the underlying formula unless helpful

### Recipe calculations

Recipe-related functionality should match the real workflow.

Prefer understandable quantities and percentages.

If the existing application already contains ingredient or product data, integrate with that data instead of creating duplicate records.

### Webshop content

Another relevant use case is a simple visual text editor for webshop content.

The editor may convert formatted content into HTML.

The webshop ultimately renders the produced HTML.

This means usability and HTML safety both matter.

A colleague should not need to manually write HTML.

## Raw HTML security

Any raw HTML functionality requires extra care.

Do not solve rendering problems by globally disabling escaping.

Distinguish:

- Markup generated by trusted application code
- Markup produced by an approved editor
- Arbitrary user-controlled HTML

Where practical:

- Allowlist supported formatting
- Strip or reject unsafe elements
- Reject script-capable attributes
- Validate URLs
- Prevent JavaScript execution
- Keep raw rendering narrowly scoped

Preserve normal Twig escaping everywhere else.

## Security priorities

Security is a high-priority project requirement.

Always consider:

- Authentication
- Authorization
- Validation
- Ownership
- Escaping
- CSRF
- Injection
- User-controlled identifiers
- File handling
- Sensitive errors
- Destructive actions
- Raw HTML

Security should be implemented server-side.

Frontend controls are a usability layer, not a security boundary.

## Usability priorities

The main users are non-technical.

Features should therefore prioritize:

### Clarity

Users should understand:

- What they need to enter
- What an input means
- Which units apply
- What action to take
- What the output represents

### Useful feedback

Validation errors should explain what needs to be corrected.

Avoid developer-oriented messages.

Prefer:

"Enter a percentage between 0 and 100."

over messages such as:

"Invalid float value."

### Contextual help

When a field or calculation may not be obvious, provide help close to the input.

Possible approaches include:

- Short descriptions
- Tooltips
- Question-mark icons
- Examples

Do not make users search separate documentation for a simple form field.

### Practical output

Results should be easy to:

- Read
- Copy
- Reuse
- Paste into the webshop
- Verify before submission

### Dangerous actions

Actions that could remove or overwrite important information should be clearly presented.

Use confirmation where appropriate.

Authorization must still be enforced on the server.

## Reliability

Expected failure cases should be handled deliberately.

Examples:

- Record not found
- Invalid input
- Missing required data
- Unauthorized user
- Forbidden action
- Duplicate operation
- Database failure
- Invalid state transition

Do not allow routine problems to produce unexplained application crashes.

## Testing philosophy

Tests should provide real confidence.

Prefer tests that protect behaviour users depend on.

Examples:

- A calculation returns the expected result
- An unauthorized user cannot perform a protected action
- Invalid form data produces useful validation
- Missing records return the intended state
- A bug cannot reappear after being fixed

Do not weaken tests simply to satisfy current implementation.

If a valid test exposes a bug, fix the bug.

## Maintainability

New functionality should feel like a natural part of the existing project.

Prefer:

- Existing naming conventions
- Existing folder structure
- Existing abstractions
- Existing validation patterns
- Existing UI patterns
- Existing test setup

Avoid unnecessary architectural novelty.

More advanced patterns are acceptable when they clearly improve substantial logic and still fit naturally into the existing codebase.

## Practical decision making

Make obvious low-risk decisions independently.

Examples:

- Match existing button styles
- Follow existing repository naming
- Use the existing flash-message mechanism
- Follow existing route naming
- Place a Twig file next to similar templates

Ask before important decisions involving:

- Permission models
- Permanent deletion
- Recoverable deletion
- Data ownership
- Major workflow changes
- Important error behaviour
- Security
- Persistent data changes
- Breaking behaviour
- New infrastructure

## Quality expectations

A feature is not ready merely because the code compiles.

It should:

- Work in the actual page
- Use the correct existing data
- Be understandable to colleagues
- Handle errors clearly
- Be secure
- Be maintainable
- Have meaningful tests
- Pass the project's configured quality checks

## Communication preferences

Keep responses short and direct.

Use bullets when useful.

When explaining something:

- Give the answer first
- Include only details that help me understand or act
- Reference real files/classes/functions when relevant

Avoid filler and unnecessary tutorials.
